## 1. 产品概述

### 1.1 产品定位

千丝傀智是一个面向多模型的分发网关。以前端策略为引线，智能区分用户意图；将请求分发到最合适的模型，统一调度、额度可控，提供一站式多模型接入与分发能力。

### 1.2 产品 slogan

> 一线分两路，双傀各承长

### 1.3 对外介绍文案

千丝傀智以前端策略为引线，智能区分用户意图，将请求分发到最合适的模型：代码难题交给擅长代码的模型，情感闲谈交给擅长对话的模型。平台支持接入数十种模型，统一调度、额度可控，是一站式多模型分发网关。

### 1.4 产品核心价值

```text
+------------------------------------------------------+
|                     核心价值                          |
+------------------------------------------------------+
|  1. 统一入口    OpenAI 兼容协议，接入即用             |
|  2. 智能路由    按请求内容与模型能力自动分发          |
|  3. 能力画像    模型互评 + 平台数据构建能力矩阵       |
|  4. 成本可控    统一额度、流量包、用量与成本统计      |
|  5. 运营闭环    供应商、模型、用户、额度全流程管理    |
+------------------------------------------------------+
```

### 1.5 核心概念

| 概念 | 说明 |
|---|---|
| 供应商 | 提供模型能力的上游服务方，如 DeepSeek、豆包、OpenAI 等 |
| 模型 | 供应商下的具体模型，是路由和计费的最小单位 |
| Go 网关 | 本项目 Go 数据平面（API/Gateway/Worker 进程），负责鉴权、分类调用、模型选择和透明转发 |
| Laya 分类运行时 | 上游 `NandhaKishorM/laya` Python typed-decision 服务；由交付系统本地安装和管理，仅负责请求意图分类 |
| 傀儡 | 对已接入模型的拟称，各自具备不同的优势与成本 |
| 能力画像 | 通过模型自评/互评和平台数据形成的模型能力评分 |
| 评分版本 | 一次评分刷新产生的模型能力快照 |
| 流量包 | 面向用户发放的额度包，通过兑换码激活 |
| 统一额度 | 用户侧使用的统一金额计量单位 |
| API Key | 用户调用网关的凭证 |

## 2. 产品目标与范围

### 2.1 产品目标

- 支持自动发现和手动添加几十种模型。
- 通过统一模板让模型互评，构建可比的能力画像。
- 依据请求内容和模型画像进行智能分发。
- 提供管理端和用户端两个平台入口。
- 兼容 OpenAI 协议，用户可用现有客户端接入。
- 通过流量包、兑换码和统一额度实现用量与成本控制。
- 保证转发时后端缓存（cache）能够生效。

### 2.2 首版范围（In Scope）

- 供应商与模型管理。
- 模型自动发现与手动接入。
- 模型统一模板互评与评分刷新。
- 智能路由与指定模型访问；自动路由使用本地 Laya 分类运行时。
- Laya 分类运行时的安装、版本/权重管理、健康检查与故障回退。
- OpenAI 兼容 API。
- 管理端与用户端。
- API Key 体系。
- 流量包、兑换码、额度预扣与结算。
- 用量、成本、延迟、错误统计。
- 权限、限流与安全保护。

### 2.3 非目标（Non-Goals）

- 首版不做多模型并行生成后自动合并回答。
- 首版不采用强化学习自动训练路由器。
- 首版不自动改写用户 Prompt。
- 首版不让模型自述决定官方价格或真实延迟。
- 首版不要求支持所有非 OpenAI 协议。
- 首版不默认保存用户完整请求内容和响应正文。

## 5. 功能需求

### 5.1 供应商管理

#### 5.1.1 功能描述

管理员可配置、测试和启停模型供应商。

#### 5.1.2 功能点

| 编号 | 功能 | 说明 |
|---|---|---|
| PM-01 | 新增供应商 | 填写名称、类型、Base URL、认证方式、密钥 |
| PM-02 | 编辑供应商 | 修改连接信息和状态 |
| PM-03 | 连通性测试 | 校验密钥与地址是否有效 |
| PM-04 | 启停供应商 | 停用后其模型不参与路由 |
| PM-05 | 查看供应商 | 查看其下模型与用量 |
| PM-06 | 删除供应商 | 删除前需校验无依赖或确认影响 |

#### 5.1.3 字段定义

```text
供应商名称
供应商类型（OpenAI 兼容 / 其他）
API Base URL
认证方式（Bearer / 其他）
API Key / Secret（加密存储、脱敏展示）
协议类型
所属区域
状态（启用 / 停用）
创建时间 / 更新时间
```

#### 5.1.4 业务规则

- 供应商密钥必须加密存储。
- 密钥不得在页面完整显示，不得进入日志。
- 停用供应商时，其模型全部不可参与自动路由。
- 删除供应商需校验是否仍有可用模型或历史引用。

### 5.2 模型管理

#### 5.2.1 功能描述

支持自动发现和手动添加模型，统一进入模型目录。

#### 5.2.2 功能点

| 编号 | 功能 | 说明 |
|---|---|---|
| MM-01 | 自动发现模型 | 调用供应商模型列表接口 |
| MM-02 | 手动添加模型 | 无列表接口时手工录入 |
| MM-03 | 模型元数据同步 | 同步上下文、能力、价格 |
| MM-04 | 模型状态管理 | 启用 / 停用 / 不可用 |
| MM-05 | 触发评分刷新 | 进入评分流程 |
| MM-06 | 查看模型画像 | 查看评分、优劣势、用量 |

#### 5.2.3 字段定义

```text
模型名称
所属供应商
模型标识（模型 ID）
上下文长度
支持的输入类型（文本 / 图片 / 其他）
是否支持流式
是否支持工具调用
输入价格 / 输出价格
能力标签
当前评分版本
状态（发现中 / 评估中 / 可用 / 不可用 / 已停用 / 评估失败）
成功率 / 平均延迟 / 缓存命中情况
创建时间 / 更新时间
```

#### 5.2.4 业务规则

- 自动发现只能获得模型存在性和部分技术元数据。
- 模型能力主要由评估机制生成，不要求管理员填写。
- 供应商删除模型时，标记不可用，不删除历史记录。
- 停用模型不参与自动路由，但仍可在管理端查看。
- 关键原则：**管理员只提供连接信息，不提供“模型适合什么”。**

### 5.3 模型能力评估与评分

#### 5.3.1 功能描述

通过统一模板让每个模型评价自身及平台已接入的其他模型，生成结构化能力评分。

#### 5.3.2 评估机制

```text
                 +----------------------+
                 | 平台模型注册中心      |
                 +----------+-----------+
                            |
                            v
                 +----------------------+
                 | 生成统一评估模板      |
                 | 包含全部已接入模型    |
                 +----------+-----------+
                            |
            +---------------+----------------+
            |               |                |
            v               v                v
       发给模型 A       发给模型 B       发给模型 C
       (全部模型)       (全部模型)       (全部模型)
            |               |                |
            v               v                v
       A 的自评/互评    B 的自评/互评    C 的自评/互评
            |               |                |
            +---------------+----------------+
                            |
                            v
                 +----------------------+
                 | Go EvaluationService |
                 | 汇总并生成评分快照    |
                 +----------------------+
```

#### 5.3.3 评估输入

- 统一的模型清单快照。
- 统一的评分维度。
- 统一的输出结构（JSON Schema）。
- 仅“当前评估者是谁”不同。

#### 5.3.4 评分维度

```text
基础能力：
- coding（代码）
- reasoning（推理）
- writing（写作）
- translation（翻译）
- summarization（摘要）
- casual_chat（闲聊）
- emotional_support（情感支持）
- vision（视觉）
- tool_calling（工具调用）
- structured_output（结构化输出）

工程指标（由平台提供，非模型自述）：
- 上下文长度
- 流式支持
- 实际延迟
- 错误率
- 成本效率
- 可用性
```

#### 5.3.5 结构化输出示例

```json
{
  "evaluatorModel": "model-a",
  "evaluatedModels": [
    {
      "modelId": "model-a",
      "capabilities": {
        "coding": 0.88,
        "reasoning": 0.82,
        "writing": 0.76,
        "translation": 0.70,
        "casualChat": 0.64,
        "vision": 0.00,
        "toolCalling": 0.80
      },
      "advantages": ["代码分析较强", "结构化输出稳定"],
      "disadvantages": ["情感闲聊自然度一般"],
      "recommendedTasks": ["代码调试", "技术解释"],
      "notRecommendedTasks": ["长时间情感陪伴"],
      "confidence": 0.72,
      "reasoning": "..."
    }
  ]
}
```

#### 5.3.6 评分汇总

```text
最终能力分 =
    模型自评         （权重较低）
  + 其他模型互评     （权重较高）
  + 标准能力测试     （后续引入）
  + 平台真实运行数据 （后续引入）
```

首版可先采用：

```text
最终能力分 = 自评 × 30% + 其他模型互评 × 70%
```

#### 5.3.7 防偏差机制

- 保存每一次评估的原始记录（评估者、被评估者、维度、分数、理由、时间）。
- 要求返回置信度。
- 对异常评分（如给所有竞品打 0 分）降低评价者权重。
- 自评与互评分开存储、分开加权。
- 评分结果不因一次调用而永久生效，需按版本发布。

### 5.4 评分刷新

#### 5.4.1 触发方式

管理员通过平台统一的刷新入口，手动点击触发。

#### 5.4.2 刷新流程

```text
1. 管理员点击“刷新模型评分”
2. 创建刷新任务 ID
3. 读取当前已启用模型
4. 固定模型清单与元数据快照
5. 固定模板版本和评分规则版本
6. 为每个模型创建评估任务
7. 并发调用所有模型
8. 校验每个模型返回的结构化数据
9. 记录成功、失败、超时、错误原因
10. 汇总自评与互评结果
11. 生成新的评分快照版本
12. 判断是否达到发布阈值
13. 原子发布新评分版本
14. 保留旧版本以便回滚
```

#### 5.4.3 评分版本与切换规则（关键）

```text
当前评分版本 V1
        |
        | 管理员点击刷新
        v
后台生成评分版本 V2
        |
        +--> 用户请求继续使用 V1
        +--> 并发评估所有模型
        |
        v
V2 校验完成
        |
        v
原子切换：V1 --> V2
```

- 刷新期间**继续使用旧评分**，不中断线上请求。
- 新评分完成后**一次性原子切换**，不逐个更新。
- 刷新失败时**继续使用旧评分**。
- 保留历史版本，支持回滚。

#### 5.4.4 部分失败处理策略

```text
达到最低发布阈值：
    发布新评分
    成功模型使用新评分
    失败模型沿用旧评分

未达到最低发布阈值：
    整体刷新失败
    继续使用旧评分版本

新模型无历史评分且本次失败：
    暂不参与自动路由
```

#### 5.4.5 任务状态

```text
整体任务：评估中 / 已发布 / 已失败 / 已取消
单个模型：pending / running / succeeded / timeout / rate_limited / invalid_output / unavailable / cancelled
```

#### 5.4.6 并发与资源控制

- 评估任务使用独立并发池，不与用户请求争抢资源。
- 限制每个模型最大 token、重试次数和超时时间。
- 记录评估本身产生的供应商成本。

### 5.5 智能路由（Go RoutingService + 本地 Laya 分类运行时）

#### 5.5.1 功能描述

Go RoutingService 在 `model=auto` 时调用本地 Laya 分类运行时取得意图标签/置信度，再结合版本化意图映射、模型能力画像、成本、延迟、可用性和管理员策略选择目标模型。Laya 不直接选择供应商模型；最终硬约束与排序均由 Go 执行。

#### 5.5.2 路由流程

```text
用户请求
   |
   v
识别任务需求（能力标签）
例如：coding >= 0.80
   |
   v
硬约束过滤（能力 / 上下文 / 模态 / 工具 / 权限 / 可用性）
   |
   v
剩余候选模型
   |
   v
综合评分（能力 + 成本 + 延迟 + 稳定性 + 管理员策略）
   |
   v
选择模型
```

#### 5.5.3 路由决策结构

```json
{
  "intent": "coding",
  "requiredCapabilities": ["coding"],
  "excludedCapabilities": [],
  "candidateModels": [
    { "model": "model-a", "score": 0.91, "reason": "代码能力强，价格中等" },
    { "model": "model-b", "score": 0.86, "reason": "代码能力强，价格较低" }
  ],
  "selectedModel": "model-a",
  "confidence": 0.91
}
```

#### 5.5.4 指定模型

用户可显式指定模型：

```text
model = auto        -> Go 调用本地 Laya 分类，再由 RoutingService 过滤/排序
model = xxx         -> 权限与状态校验后直接转发，不调用 Laya 分类服务
```

- 指定模型不可用或无权限时，默认**返回错误**。
- 自动降级作为单独策略，且必须记录。

#### 5.5.5 低能力/低成本模型倾向（管理端配置）

**定义：** 管理员配置的内部路由策略，控制在多个模型满足请求最低能力要求时，Go RoutingService 对低成本、低能力模型的选择倾向程度；该策略不下发给 Laya 分类运行时。

**关键规则：**

```text
最终路由分数 =
    能力匹配分
  + 成本偏好分
  + 延迟偏好分
  + 稳定性分
  + 管理员策略修正
```

- 该配置**仅管理员可见**，用户不可查询、不可覆盖。
- 倾向度越高 → 成本因素权重越高。
- **无论倾向度如何，模型必须先满足最低能力阈值。**
- 高风险任务（复杂代码、安全、法律、医疗等）可强制质量优先。

**配置形式建议：**

```text
低成本模型倾向度：0 - 100
0   = 尽量选择能力最强模型
50  = 质量与成本平衡
100 = 满足最低能力前提下尽量选低成本模型

字段：routing_policy.low_capability_bias（管理端 API 参数 lowCapabilityBias）
```

#### 5.5.6 路由可观测性

- 记录最终选择模型、路由原因、候选模型。
- 用户侧默认不暴露内部评分和策略公式。

### 5.6 透明转发与缓存

#### 5.6.1 功能描述

Go 网关负责判断和代理，尽量保留原始请求，使目标模型后端 cache 生效；本地 Laya 分类运行时只接收分类副本，不改写用户原始请求。

#### 5.6.2 核心规则

```text
原始请求
    |
    v
路由分析副本（仅用于判断目标模型）
    |
    v
原始请求尽量原样转发（仅替换目标 endpoint）
```

**必须保留：**

- 消息内容
- system prompt
- 消息顺序
- 供应商专用缓存字段
- 请求头中的兼容字段
- 流式语义

**禁止：**

- 无必要地重写用户消息
- 改变消息顺序
- 删除供应商扩展字段
- 破坏缓存标识

#### 5.6.3 流式响应

- 使用增量转发。
- 不等待完整响应后再返回。
- 保留流式数据格式。

## 6. 非功能需求

### 6.1 安全

- 供应商密钥加密存储。

```text

```

- 文本语义分类由本地 Laya 完成；Go 优先使用请求结构特征，分类输入仅为最新用户消息和必要上下文，不向额外云端分类器发送全文。分类副本长度受 Laya checkpoint 上下文限制。
- 用户敏感数据需明确处理策略。

### 6.3 限流

```text

单模型并发数

```

- 评分版本支持回滚。

### 6.5 性能

- 规则判断应低延迟。
- 流式响应及时转发。
- 评估任务不占用线上请求资源。

### 6.6 可观测性

- 记录路由结果、命中模型、耗时、token、费用、失败原因。
- 保留评分版本、评估原始记录、刷新任务结果。

## 10. 关键参数决策（基于行业实践）

以下参数已按主流 AI 网关（OpenRouter、LiteLLM、one-api/new-api 等）的通用做法拍定，作为首版默认值。

### D-01 额度单位

**决策：** 用户侧统一以**人民币元**展示与结算，支持小数；内部以整数最小单位（微元，即 1e-6 元）存储，避免浮点误差。

**依据：** 按金额计量是多模型网关的通用做法（OpenRouter 使用 credits、LiteLLM 使用美元额度）。用整数最小单位存储是金融计费的标准实践，避免浮点累积误差；展示层再格式化为元。

### D-02 指定模型不可用时的行为

**决策：** 默认**直接返回错误**（遵循 OpenAI 兼容错误格式，模型不存在返回 `model_not_found`），不自动切换。自动降级作为需要显式开启的独立策略。

**依据：** OpenRouter、one-api 等在用户显式指定模型时均直接报错，避免用户以为调的是 A 模型、实际被路由到 B 模型。自动切换会造成黑盒行为、额外费用和输出风格突变。

### D-03 评分发布的最低成功率

**决策：** 有新评分覆盖的模型占比 **≥ 80%** 才发布新版本；低于该阈值整体不发布，继续沿用旧评分。

**依据：** 与行业对批量任务“多数成功即可发布、失败项回退”的处理一致，既能容忍个别模型超时，又避免大面积失败污染能力矩阵。

### D-04 评估预算限制

**决策：**

```text
单模型单次评估 max_tokens：2000
评估并发：5
单模型超时：60 秒
同一刷新任务去重：刷新进行中不可重复触发
每日自动/手动刷新上限：默认 1 次，可配置
```

**依据：** 模型互评会真实消耗供应商额度，必须限量。并发和超时向 LiteLLM 等网关的默认行为看齐，防止几十个模型同时调用拖垮网关或账单。

### D-05 用户是否可见实际模型名称

**决策：**

```text
API 响应中的 model 字段：返回实际使用的模型名（兼容客户端语义）
用户控制台：展示实际模型
用户可见范围：仅模型名
用户不可见：内部评分、候选排名、路由公式、低成本倾向值
```

**依据：** OpenRouter 在响应中返回实际模型，客户端依赖该字段做展示与计费核对，这是兼容性要求。但内部能力评分和策略属于平台壁垒，须保持不可见。

### D-06 请求内容记录

**决策：** 默认**只记录元数据**（用户、Key、模型、时间、token、费用、延迟、状态）；完整请求内容默认**不记录**。如需开启内容日志，需管理员显式配置、受权限控制，默认保留 **7 天**。

**依据：** Prompt 中可能包含代码、密钥、企业资料和个人隐私。Helicone、LiteLLM 等默认对内容做可选、可脱敏处理，合规平台默认不落全文。

### D-07 首版协议与模态范围

**决策：** 首版支持

```text
GET  /v1/models
POST /v1/chat/completions
流式响应
工具调用（tool calling）
```

**暂不支持（后续版本）：**

```text
/v1/embeddings
/v1/completions
图片输入
音频输入
```

**依据：** chat completions + 流式 + 工具调用已覆盖绝大多数聊天与 Agent 客户端，是网关的最小可行兼容集；embeddings 和多模态按需增量接入。

### D-08 多管理员与组织/团队额度

**决策：** 首版支持**多管理员 + 基于角色的权限控制（RBAC）**，权限至少分为：模型管理、用户管理、额度管理、日志查看。**组织/团队级额度**顺延到第二版。

**依据：** 多管理员和最小权限是运营安全底线（供应商密钥、用户额度都属高危操作）；组织/团队模型会显著增加账户与额度层级复杂度，适合在核心链路稳定后再引入。

### 决策小结

| 编号 | 结论 |
|---|---|
| D-01 | 元展示，微元（1e-6）整数存储 |
| D-02 | 指定模型不可用默认报错，降级需显式开启 |
| D-03 | 发布阈值 80% |
| D-04 | 单模型 2000 token、并发 5、超时 60s、刷新去重 |
| D-05 | API 与用户端可见实际模型名，内部评分不可见 |
| D-06 | 默认只记元数据，内容日志可选开启、默认保留 7 天 |
| D-07 | 首版 models + chat/completions + 流式 + 工具调用 |
| D-08 | 首版多管理员 + RBAC，组织/团队额度顺延 |

## 12. 闭环补充约定

本节将计费、路由、兼容性、认证和评分发布边界固化为首版验收规则；与前文较宽泛描述不一致时，以本节为准。

### 12.1 计费与请求终态

- 供应商返回且校验通过的 usage 是唯一最终计费依据。没有可信 usage 时不得估算收费：无可信用量则释放预扣；有可信部分用量则仅结算该部分并释放余额。
- 预扣按估算输入用量和请求允许的最大输出用量计价，在供应商调用前完成；不足以覆盖预扣或超过平台请求上限时拒绝调用。
- 客户端断开、网关超时、供应商失败均尽力取消上游。自动重试只允许在确认上游未接受请求且尚未向客户端发出响应时；执行状态不明时不得重试，除非供应商幂等能力可保证不重复执行。
- 流式首字节发出后，错误只能以 SSE error 事件报告；客户端断开/上游中断按实际可验证 usage 结算，否则释放预扣。请求终态和账务结算通过 request_id 幂等，最多产生一笔最终扣费。
- 相同幂等键绑定相同请求摘要；相同键不得重复执行/扣费，进行中的请求返回 409 `request_in_progress` 和原 request_id，已完成请求返回 409 `idempotency_replay` 和原 request_id（不要求保存/重放正文）；不同摘要返回 409 `idempotency_conflict`。

### 12.2 路由与评分

- 先按可用状态、Key 权限、上下文、工具/模态能力及必需能力阈值做硬过滤，再对合格模型评分；候选为空返回 503，不得静默放宽约束。
- 能力分为 0..1，各必需能力取算术平均作为能力匹配分；能力数据缺失视为不合格。成本、延迟对合格候选集 min-max 反向归一化，维度全相等时均记 1；稳定性取近 7 天成功请求比例，样本少于 20 时记 0.5；缺失成本/延迟记 0。以 `b=low_capability_bias/100` 计算默认权重：能力 `0.70-0.50b`、成本 `0.10+0.60b`、延迟 `0.10`、稳定性 `0.10`。高风险质量优先时使用能力/成本/延迟/稳定性权重 `0.70/0.10/0.10/0.10`。
- 同分依次按稳定性高、成本低、模型 ID 字典序小决定。明确的工具/模态要求优先于意图推断；意图置信度低于 0.60 时按通用对话路由。高风险规则首版命中明确的安全漏洞/攻击分析、数据库迁移/破坏性数据修改、法律意见、医疗诊断请求；按版本化规则匹配请求文本并审计，不由模型自由判断。

### 12.3 评分发布

刷新只生成候选版本，不自动改变线上版本。评分发布权限管理员显式发布；新旧版本切换在事务内原子完成。运行时快照更新失败时继续使用旧快照并重试，新实例启动从数据库读取已发布版本；发布仅在新快照可用后确认成功。回滚使用相同流程。

发布成功率分母为刷新开始时冻结的启用参与模型数，分子为本次产生且通过结构校验的新评分模型数；历史评分回退不计入新评分成功率。低于 80% 不可发布，无历史有效评分的新模型不参与自动路由。

### 12.4 接口、安全与验收

- 标准 API 字段必须落在网关明确支持的字段集合内；不支持字段返回 400。供应商扩展字段仅按管理员配置白名单透传，未授权扩展字段拒绝，不允许适配层静默改变请求语义。
- 用户/管理员会话使用服务端可撤销的不透明令牌，数据库仅存令牌摘要，绝对有效期默认 24 小时；密码使用 Argon2id。登出、禁用账户或撤销会话立即失效。所有额度调整、权限变更、供应商凭证变更、评分发布/回滚写不可变审计记录。
- 全局、用户、Key、供应商、模型限流超限返回 429 和 `Retry-After`；限流存储不可用时 fail-closed。
- 首版验收必须覆盖并发预扣、重复幂等键、无 usage、部分流式用量、客户端断开、上游超时/错误、评分部分失败与回滚、运行时快照更新失败及越权访问。
- 组织/团队额度、embeddings、多模态输入和多模型答案合并仍为非目标，不纳入首版验收。
